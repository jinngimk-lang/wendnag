# AegistonTeam 试点与 ROI 评估表 V1

## 一、试点目的

试点不是免费做一个完整项目，也不是展示一次 AI 生成代码。它应回答一个商业问题：

**在一项边界清楚、验收标准一致的软件研发任务上，AegistonTeam 是否能带来可测量的协作、交付或成本价值，同时满足质量和风险要求？**

## 二、优先选择什么任务

适合的候选任务：
- 一个独立功能或模块；
- 一个明确的缺陷修复；
- 一个接口适配或数据转换任务；
- 一组可重复的测试补齐任务；
- 一项需求变化明确、影响范围可控的修改。

不适合首期试点：
- 直接改生产核心链路；
- 需求边界不清、验收标准无法确定；
- 依赖多个尚未验证的系统集成；
- 涉及高敏数据但没有安全评估；
- 必须依赖未实现功能才能完成；
- 没有业务/研发负责人承担验收。

业务应用开发（如售后、审批、门店系统）可以作为 AegistonTeam 参与的软件项目，但销售必须明确：客户购买的是软件研发协作平台，不是已经预制好的行业业务系统。

## 三、试点前必须约定

| 项目 | 客户与我方需要确定 |
|---|---|
| 目标任务 | 任务描述、业务背景、范围和排除项 |
| 现有基线 | 相同或可比任务的人工、周期、返工、验收 |
| 产物 | 需求、任务、代码/文档、测试、评审和版本记录中哪些实际适用 |
| 验收标准 | 功能、代码质量、测试、规范、业务验收和安全要求 |
| 数据范围 | 脱敏、合成或允许使用的数据；不允许访问的内容 |
| 参与人员 | 客户业务、产品/研发、IT/安全；我方销售、售前、交付 |
| 运行环境 | 当前版本可支持的环境、工具和权限 |
| 成本 | 人工、平台、模型/算力、实施、集成和运维 |
| 时间 | 双方可履约的开始、检查点和结束时间 |
| 退出条件 | 不达标、数据风险、范围变化或资源不足时如何停止 |

## 四、试点指标

| 维度 | 指标 | 记录方式 |
|---|---|---|
| 交付速度 | 任务从确认到验收的总周期 | 记录开始、等待、结束时间 |
| 人工投入 | 人类实际参与小时 | 分需求、提示/监督、开发、Review、测试和协调 |
| 质量 | 首次验收通过、缺陷和返工 | 使用客户现有质量标准 |
| 变更 | 一次真实需求变化的处理结果 | 记录影响、修改、回归和再次验收 |
| 协作 | 交接次数、等待时间、任务阻塞 | 用任务日志和会议记录 |
| 可控性 | 人工审批、权限边界、失败恢复 | 记录实际操作与测试结果 |
| 成本 | 平台、模型/算力、工具和实施成本 | 以真实账单/计量为准 |
| 采用 | 使用者是否愿意继续使用 | 访谈、实际活跃和复用意愿 |

## 五、ROI 计算口径

对同类任务建立基线和试点结果。

基线总成本：
- 人工投入 × 对应人力成本；
- 评审、返工和等待造成的额外成本；
- 原有工具和基础设施的可归因成本。

试点总成本：
- 试点人工投入 × 对应人力成本；
- 平台许可/订阅；
- 模型/算力；
- 实施、集成、安全评估和培训；
- 运维与支持。

净收益 = 可确认的基线成本 − 试点总成本。

ROI = 净收益 ÷ 试点总成本。

注意：
- 释放工时不自动等于现金节省；若人员仍在岗，应单独报告“释放产能”。
- 不能把开发时间减少直接当成项目交付周期减少，必须记录等待和依赖。
- 不同任务难度不同，不能把单个小任务的结果外推为全公司提效比例。
- 如果试点包含一次性实施成本，应区分首期和规模化后的边际成本。
- 只有客户认可的同类基线和验收结果才能进入正式商业案例。

## 六、试点决策门槛

开始前由双方填写具体数值或可判断标准，不能事后移动目标：

- 业务验收：必须满足哪些功能/流程条件？
- 工程验收：测试、Review、规范和安全要求是什么？
- 效率验收：周期、人工投入或返工改善达到什么程度？
- 风险验收：权限、数据、失败处理是否可接受？
- 经济验收：总成本和后续扩展成本是否可接受？
- 采用验收：团队是否愿意继续使用？

结论分为：
1. **继续**：关键验收通过，存在明确下一阶段任务；
2. **调整**：方向有价值，但某些能力/条件需补齐；
3. **暂缓**：客户条件、预算或时间未准备好；
4. **停止**：核心价值不成立或风险不可接受。

## 七、试点后必须交付的材料

- 任务与验收范围；
- 基线和试点数据；
- 真实运行证据与未完成项；
- 质量和安全评估；
- 投入与成本明细；
- 客户各岗位结论；
- 是否继续、调整或停止；
- 若继续，正式商务范围、价格结构、采购流程和双方责任。

未经客户书面授权，不将试点名称、数据、截图或成果用于公开营销。
