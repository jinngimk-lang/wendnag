# 大型企业销售方案 V2 — V1 审计报告

审计日期：2026-11-06  
审计对象：大型企业销售方案V2_完善版.pptx（91 页）

## 一句话结论

这是一份有实操价值的**大客户销售执行手册**，但它把内部销售运营和客户产品提案装进同一套 91 页材料。若把它直接当作客户版销售 PPT，产品说服力、证据、商业论证和决策闭环都不够。

正确做法不是简单删页或换皮，而是保留内部手册，再建立一套更短、更有证据、更能推动采购的客户版主 Deck。

## 做得好的部分

1. **销售过程完整**：账户准备、客户分类、渠道拓展、岗位沟通、需求访谈、定向提案、试点、采购、交接和复盘均有覆盖。
2. **尊重客户事实**：第 9–12 页强调区分公开事实、场景假设和客户确认信息；阶段推进有依据。
3. **客户沟通可执行**：第 62–66 页有 45 分钟首次交流、需求四问、公司介绍、交接和会后跟进。
4. **演示思路正确**：第 73–74 页把一条完整任务和一次真实需求变更作为核心展示。
5. **试点治理较好**：第 77–80 页覆盖范围、材料、共同验证、投入记录和多岗位评估。
6. **内部经营节奏明确**：第 88–91 页有 90 天计划、每周账户复盘和卡点处理。

## 关键问题

### P0 — 必须解决

**1. 受众与目标混杂**

- 第 1 页称“大客户销售方案”，副标题却是“线下拓展、沟通行为、企业分类、方案与提案 PPT”。
- 第 2 页按八章组织，后续 24 条渠道、教学活动、销售话术和团队复盘都属于内部工作。
- 客户决策者不需要阅读如何找人、办活动、管理销售机会。

处理：保留 91 页内部手册；新建 12–15 页客户版主 Deck。

**2. 产品品类与差异化不够清楚**

- 第 4 页用三段说明数字 FDE、行业规则、UI/UX、代码测试和交付，但没有一句清晰的品类定义。
- “数字 FDE”未解释，企业客户可能不知道它是什么、做什么、与项目经理/产品经理/开发 Agent 的关系是什么。
- 没有充分解释 AegistonTeam 与通用 AI 助手、编码助手、单体 Coding Agent、传统研发管理平台的边界。

处理：主品类采用“企业级人机协同软件开发平台”；数字 FDE 作为需求澄清和任务编排机制；用一张对照图说明“从个人辅助到团队级交付”的差异。竞品名称和能力比较须重新核验后再加入。

**3. 产品证据不足**

- 全套 PPT 的主视觉以插画、表格和流程文字为主。
- 没有呈现真实 AegistonTeam 产品界面、真实多智能体运行轨迹、真实代码差异、测试报告、人工评审或可验收交付物。
- 第 4 页的浏览器/流程插画不是产品真实界面。
- 第 73 页的 25 分钟演示设计是好结构，但仅有计划，没有真实运行证据。

处理：产品证据页必须采用真实截图/录屏/代码/测试/任务日志；原型需明确标注“交互原型/设计演示”，不得伪装成生产运行。

**4. 产品场景与软件开发平台定位有偏差**

- 第 69–72 页的制造售后、软件集成、集团部门、连锁运营提案，主要从业务流程应用角度描述。
- 第 78 页试点任务是设备售后报修、审核、派单和处理。
- 这类场景可以是平台开发的应用对象，但没有充分显示“软件研发团队如何用 AegistonTeam 完成软件开发任务”。

处理：把主演示改成软件研发任务：需求澄清 → 任务拆解 → 人机/多智能体分工 → 代码/测试产物 → 人工评审 → 变更与回归验证 → 验收。行业业务应用仅作为平台构建的软件项目示例，并明确这是“开发一个应用”，而不是 AegistonTeam 本身就是售后/审批业务系统。

**5. 缺少商业决策闭环**

客户版结构没有充分呈现：
- 可验证的业务价值和 ROI 计算；
- 当前研发方式与新方式的同类任务基线；
- 部署、数据流、模型调用、权限、审计、备份和运维证据；
- 现有工具如何保留/集成；
- 软件授权/订阅、实施、集成、算力、硬件和服务的商业结构；
- 采购范围、验收、退出条件和明确 CTA。

处理：把这些内容加入客户版主 Deck 或岗位附录；价格和 SLA 只能在真实成本与服务能力核验后承诺。

### P1 — 高优先级

**6. 目标行业过宽**

第 5 页和第 69–72 页并列设备制造、软件集成、集团机构、连锁运营，但产品当前主定位是软件开发和项目交付。2026-11-04 内部增长方案建议首阶段聚焦一个区域/一个行业，优先研发与项目交付部门。

处理：首轮主攻软件/系统集成企业与企业内部研发/数字化部门；制造、连锁等场景作为有研发团队或明确应用开发需求时的模块，不作为并列泛化承诺。

**7. 竞争替代方案没有进入销售叙事**

客户会问：为什么不直接使用现有编码助手、Coding Agent、Git 平台、项目管理工具或外包团队？现有 PPT 没有系统回答。

处理：用“个人编码加速 / 单任务 Agent 执行 / 研发流程管理 / 人机混编团队交付”类别矩阵回答；不未经核验地写具体厂商的功能结论。

**8. ROI 评估还停留在记录层面**

第 79 页要求记录实际投入、等待和返工，方向正确，但缺少统一指标与计算口径。

处理：至少记录任务周期、人工投入、首次验收通过率、返工轮次、人工复核时间、模型/算力成本、部署集成成本、每份已验收产物成本和持续使用意愿。用同类多次任务对比，不用一次演示推导普遍提效比例。

**9. 企业技术评估深度不足**

第 75–76 页提及系统、数据、环境和变更，但尚未形成企业技术准入材料。

处理：补数据流图、模型/外部服务调用清单、权限矩阵、日志样例、密钥与代码访问边界、失败恢复、备份、部署拓扑、运维责任、代码/IP 归属和安全测试结果；未验证项标待核实。

### P2 — 视觉与表达优化

**10. 版式重复、内容密度偏高**

- 页面比例已确认是 16:9，不需要再次改比例。
- 第 18–46 页渠道操作页大量重复“六步骤 + 底部负责人”，信息结构相似。
- 多数页面使用相近的标题、橙色强调、表格/文本块和插画。
- 个别客户提案页（尤其第 69–72 页）三栏文字和六项提纲同时出现，层级偏多。
- 文字抽样显示部分页面最小字号约 12 pt，普通正文中位数约 16–17 pt；远距离会议室投屏时仍应进一步放大关键内容。

处理：客户版每页只保留一个主结论；正文尽量 18–22 pt；重点证据用产品界面、流程、代码/测试产物和量化图表呈现；减少通用卡通插画和表格重复。

**11. 品牌与产品素材未形成统一系统**

- AegistonTeam 与 AragonTeam 旧名称并存于公司资料。
- 原 PPT 以橙色卡通角色为主，产品原型则有深蓝/橙色和产品 UI 视觉。
- 2026-10-28 设计锚点的颜色与 HTML 原型 CSS 也存在不同色值记录。

处理：以最新正式品牌规范为准；在确认前使用临时色彩系统，并在客户版以产品 UI 和工程过程为主，吉祥物仅作辅助识别。

**12. 缺少明确结尾**

第 91 页是内部销售卡点处理表，不是客户版结束页。

处理：客户版结尾明确下一步：联合需求工作坊、技术评估、试点任务单、双方负责人和预计时间。

## 最优先的重构动作

1. 不覆盖原 91 页；将其定位为内部销售作战手册 V2。
2. 从第 4、68、73–80 页提取有价值的产品与试点逻辑。
3. 重写第 69–72、78 页为软件开发任务示例。
4. 增加真实产品/执行证据、企业技术准入、ROI、商业结构和 CTA。
5. 先制作三种视觉方向样张，独立挑战后再批量制作。
