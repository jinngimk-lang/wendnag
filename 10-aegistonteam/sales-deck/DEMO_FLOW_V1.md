# AegistonTeam 软件研发闭环演示 V1

## 演示目标

让客户在 25 分钟内看懂一件事：

**AegistonTeam 不只是生成一段代码，而是把一项研发任务组织成可分工、可评审、可验证、可继续修改的交付过程。**

演示必须使用当前真实可运行版本。若只有 UI 原型或静态流程，改为“产品共创/设计演示”，不得声称是真实多智能体执行。

## 演示场景

使用一项明确标注为“演示项目”的软件研发任务。建议选取现有演示仓库中的一个小功能或缺陷，不使用客户生产数据。

任务要求：
- 输入：原始需求/缺陷描述、现有项目背景、验收条件。
- 数字 FDE：澄清歧义、补充边界条件、整理任务和验收标准。
- 智能体：按当前真实支持的方式分工推进；角色名称以当前实际配置为准。
- 人类负责人：确认需求、审批关键动作、评审代码和最终验收。
- 产物：需求说明、任务状态、代码差异、测试结果、评审意见、版本/交付记录。
- 变更：增加一条新要求，展示影响分析、修改和回归验证。

示例题目可用“项目管理模块增加成员角色校验”或“工单系统增加批量导入与异常校验”，但必须确保演示仓库里确有对应代码和测试；没有真实实现时只作为概念题，不得假称已完成。

## 25 分钟客户定向演示

| 时间 | 演示动作 | 客户应看到的证据 | 人类确认点 |
|---|---|---|---|
| 0–2 分钟 | 先展示最终可验收的结果 | 运行页面/功能、测试结果、交付物 | 结果是否对应任务目标 |
| 2–6 分钟 | 输入原始需求，数字 FDE 澄清 | 原始输入、追问、结构化需求、验收标准 | 需求是否理解正确 |
| 6–10 分钟 | 拆分任务并组织协作 | 任务依赖、负责人/Agent 分工、状态变化 | 任务计划是否可接受 |
| 10–16 分钟 | 展示真实执行过程 | Agent 执行记录、代码差异、等待/失败/恢复 | 哪些动作需要人工批准 |
| 16–19 分钟 | 运行测试并进入人工评审 | 测试报告、失败项、评审意见、修订记录 | 是否达到验收条件 |
| 19–23 分钟 | 增加一条真实需求变化 | 影响分析、任务更新、代码/测试重新验证 | 变更是否按预期处理 |
| 23–25 分钟 | 总结交付和边界 | 产物清单、未完成项、成本/资源记录 | 是否值得进入小范围试点 |

## 现场必须展示

1. 真实产品界面，而非重绘或虚构 UI。
2. 原始需求与澄清后的结构化需求。
3. 人类与 Agent 的真实分工和任务状态。
4. 至少一个可复查代码差异。
5. 至少一个真实测试命令/报告。
6. 一次人工评审或退回修改。
7. 一次需求变更和重新验证。
8. 未完成项、失败情况和能力边界。

## 不应展示为已实现的内容

- 只有导航入口、但没有端到端实现的连接器。
- 模拟的 Token、成本、审计和任务运行数据。
- 录屏剪辑后声称为实时执行。
- 静态看板被描述为真实 Agent 执行。
- 没有测试报告却说“自动测试通过”。
- 没有部署证据却说“数据不出企业网”。
- 没有合同依据却承诺代码/IP 归属或 SLA。

## 40 分钟公开演示的扩展

2026-11-04 内部增长方案建议的公开演示节奏：
- 0–5 分钟：场景、输入和验收标准。
- 5–15 分钟：创建/进入项目，整理需求。
- 15–25 分钟：展示已验证的智能体协作环节。
- 25–32 分钟：审核成果、退回修改、归档。
- 32–37 分钟：适用边界与成本。
- 37–40 分钟：邀请客户带真实任务进入体验/试点。

若仅有原型，应将活动名称改为产品共创说明会，目标改为访谈或内测预约。

## 演示前检查清单

- [ ] 当前版本和环境可重复运行。
- [ ] 演示数据已脱敏，不含客户机密。
- [ ] 模型、工具、连接器、数据流边界已核对。
- [ ] 代码仓/分支/提交状态已确认。
- [ ] 测试命令和测试报告可复现。
- [ ] 人工确认点和 Agent 自动动作有清晰区分。
- [ ] 失败/等待/恢复路径已演练。
- [ ] 准备备用录屏，但切换时明确告知客户。
- [ ] 演示结束能给客户留下产物、问题、未完成项和下一步。
